## Description

Independent verification that the MVP is genuinely usable, not just that each phase self-reported green.

#### Repository

Read them before you start. Do not re-design what is already decided; if you must diverge, say so on this task with the reason.

#### Scope

**1. Audio fixture suite** — committed, repeatable, with known expected output:
- 30 seconds of silence (must yield zero transcript lines).
- Single speaker, clean.
- Overlapping speakers on the two tracks.
- A device switch (AirPods connect/disconnect) mid-recording.

**2. Drift check** — measure mic-vs-system alignment over a long recording and report the number in milliseconds. Gate is under 200 ms over 45 minutes.

**3. Silence-hallucination guard** — a standing regression test, not a one-time check.

**4. Signed-bundle test loop** — permission prompt appears and names meet-ai, entitlements are correct, first-run behaviour is right, and the denied-then-re-granted path works.

**5. End-to-end on a real 45-minute call** — record it, transcribe it, read the transcript, and answer the only question that matters: is this usable?

### Fixture spec — what certifies the Phase 0 exit gate

Owner: [@Tess](agent://23653fce-5de4-47b8-bc18-f2da0505fa01).
Reads from: [#document-audio-contract](TUR-4.md) revision 2 (Rune), `SPEC.md` §5/§6, `FINDINGS.md` §8.
Produced by: `just fixtures` into `crates/audio/fixtures/`.

Status: **§2, §3 and §4 are built and green** — [TUR-29](TUR-29.md), commit `20f989b`.
§5, §6 and §7 are still spec only and still blocked on the recorder existing.

The built rows assert against the Rust types in `crates/audio/src/segments.rs` —
`DriftReport`, `ChannelDrift`, `Breach`, `BoundaryGap`, `DriftError` — rather than against
`drift-check` stdout, which answered open item 4 without anyone having to fix a print
format. The exit codes in the tables below are what a future `drift-check` must map those
results to: `passes()` true → 0, false → 1, `Err(DriftError)` → 2.

Everything is in `crates/audio/fixtures/segments/<name>/segments.json`, generated by
`fixtures/generate-segments.py` and **committed** — the on-disk shape is half of what is
under test. Assertions live in `crates/audio/tests/segments_fixtures.rs`.

---

#### 0. Why these exist

`FINDINGS.md:138` — two-stream clock alignment has "no test oracle, silent failure mode,
drift only visible at the 30-minute mark". A fixture is the oracle. Each row states a
known input and the exact number `drift-check` must produce from it, so the tool is
verified against something other than its own output.

The rule I am applying throughout: **a gate that has never been observed to fail is not
known to work.** Every threshold gets a pair — one fixture just under, one just over.

---

#### 1. What gets committed vs generated

45 minutes of 16 kHz mono s16 is ~86 MB per channel. That does not go in git.

- **Committed** (a few tens of KB each; 624 KB for all 18): every `segments.json`, plus
  `fixtures/generate-segments.py` and the `just fixtures` recipe that synthesises them. The
  repo-wide `crates/audio/fixtures/*` ignore rule is amended to let `segments/` through.
- **Generated** by `just fixtures`, and **opt-in behind `FIXTURE_WAVS=1`**: the WAVs, as
  silence of the exact declared frame count. Content is irrelevant for drift — only the
  header frame count is read, for the §12 coverage check — and 2700 s of 16 kHz mono s16 is
  86 MB per channel, about 1 GB across the drift fixtures. Nothing in the built assertions
  reads a sample, so the default is off. Gitignored either way.
- **Exception**: `silence-30s.wav` and `two-speaker-60s.wav` are small and content-bearing
  (they feed transcription, not drift). Those are committed.

---

#### 2. Drift fixtures — the §11 anchor path

All synthesised against the contract's formula, per channel:

```
drift(i) = anchors[i].frames / 16000 − (anchors[i].host_ns − start_host_ns) / 1e9
```

A device clock fast by `p` ppm produces `drift = elapsed_seconds × p / 1e6`.
Over a 2700 s (45 min) recording, **200 ms is exactly 74.07 ppm** — that is the number the
gate sits on, so the boundary pair is built around it.

| Fixture | Construction | Expected `drift-check` | Exit |
|---|---|---|---|
| `drift-clean-0ppm` | both channels, frames exactly `16000 × elapsed` | max drift 0 ms, slope 0 ppm | `0` |
| `drift-pass-50ppm` | mic +50 ppm, sys 0 ppm, 2700 s | mic 135 ms, sys 0 ms, cross-track 135 ms, slope 50 ppm | `0` |
| `drift-edge-74ppm` | mic +74 ppm, 2700 s | mic 199.8 ms — **must pass** | `0` |
| `drift-edge-75ppm` | mic +75 ppm, 2700 s | mic 202.5 ms — **must fail** | `1` |
| `drift-fail-100ppm` | mic +100 ppm, 2700 s | mic 270 ms | `1` |
| `drift-common-mode-100ppm` | **both** channels +100 ppm | per-channel 270 ms each, **cross-track ≈ 0 ms** | `1` |

`drift-edge-74ppm` / `drift-edge-75ppm` together prove the threshold is where §12 claims it
is, in both directions, within 2.7 ms.

`drift-common-mode-100ppm` is the regression test for the original blocker. The pre-rev-2
quantity `(mic_frames − sys_frames) / 16000` reads **0 ms** on this fixture and would have
certified it. Assertion is therefore two-part: exit `1`, **and** the printed cross-track
number is ≈0 while the gate number is 270 ms. If a future change makes this fixture pass,
the tool has regressed to the broken metric.

Tolerance on every expected value: **±1 frame (62.5 µs)**, per §6's pad quantisation.

#### 3. Refusal fixtures — the §12 code-2 path

`drift-check` must refuse rather than flatter. Each of these asserts exit `2` **and** a
`not measurable: <reason>` line on stderr. A `0` here is a gate-certifying bug.

| Fixture | Construction | Why |
|---|---|---|
| `refuse-no-system` | `mic.wav` + `segments.json`, **no** `system.wav` | Failed tap. Rune confirmed absent, not zero-length, is the supported signal |
| `refuse-zero-rate` | `sys_rate: 0` | |
| `refuse-no-anchors` | valid segments, `anchors` key absent | Revision-1-shaped file |
| `refuse-one-anchor` | single anchor in a segment | Nothing to difference |
| `refuse-anchors-stop-early` | header declares 2700 s; anchors stop at 300 s | **F2 — was real, now fixed.** Returned `Ok` with `max_abs_ms: 3.0` and `passes: true`. Now `AnchorCoverage { uncovered_ms: 2400024.0, slack_ms: 5250.0 }` |
| `refuse-frozen-clock` | 60 anchors, all identical `host_ns`, frames still arriving | **Was real, now fixed.** `NonMonotonic` tested `now < before` and a stopped clock never goes backwards. Now `FrozenClock { anchor: 1, field: "mic_host_ns" }` |
| `refuse-frozen-clock-and-frames` | 60 anchors, identical `host_ns` **and** identical frames | **Added beyond the original seven.** The row above fails the gate loudly anyway; this one read 0 ms at every anchor and *passed*. Same `FrozenClock` refusal |
| `refuse-nonmonotonic` | anchor `host_ns` goes backwards | |

`refuse-anchors-stop-early` was the one I cared most about, and it was real: before
`435fb67` it returned a passing number for a recording whose last 2400 s nobody measured —
precisely the failure mode the anchors were added to eliminate, one level down. It was the
acceptance test for that fix and it now passes.

`refuse-one-anchor` is the **one row still unbuilt**, and not for want of a fixture: its
expected value is contested. See the open items.

#### 4. Device-switch fixtures — §5 gaps, §11 segment close

Replaces the impossible rate-change shape Rune caught in the old fixture (segment 1 at
48 kHz inside a 16 kHz WAV).

| Fixture | Construction | Asserts |
|---|---|---|
| `device-switch-400ms` | 2 segments, seg-0 close anchor present, `start_host_ns[1] − start_host_ns[0]` implies a **400 ms** unpadded gap | §11 gap formula returns 400 ms ±1 frame |
| `device-switch-no-close-anchor` | same, but seg 0's last anchor is an ordinary checkpoint 4.2 s before close | **F1 as written does not reproduce.** The gap reads 400 ms with or without the close anchor. The file is refused outright instead: `AnchorCoverage { uncovered_ms: 4200.0, slack_ms: 250.0, closed_deliberately: true }` |
| `device-switch-short-tail` | seg 1 is 8 s long, 2 anchors total | **F3 has nothing to attach to** — `DriftReport` exposes no slope. Asserts `anchors: 2` and the 3 s tail kept out of drift |
| `device-switch-drift-reset` | seg 0 at +100 ppm for 1200 s, seg 1 at +100 ppm for 1200 s | Gate number is **max over segments (120 ms, pass)**, never the sum (240 ms, fail) |

`device-switch-no-close-anchor` is a **negative** fixture: it encodes the F1 bug on purpose,
so that removing the close-anchor call site fails a test rather than degrading a number
quietly. What it actually catches is not what I predicted. I assumed the gap formula read
the last anchor; it differences the *segment* frame totals, which are current at close, so
the close anchor was never on the gap path and the gap is 400 ms either way.

The refusal is the stronger answer. Seg 0 is not the last segment, so it was closed
deliberately and gets 250 ms of ring-buffer-drain slack rather than the 5 s a `kill -9`
gets. 4.2 s of audio no anchor ever measured is a corrupt file, not a ragged shutdown.

`device-switch-drift-reset` pins the non-obvious semantics from F4 so nobody later "fixes"
`drift-check` into accumulating across re-anchored segments.

---

#### 5. Crash fuzzing — §7's inequality

Not a static fixture; a harness. Run `meet-rec` against synthetic input and `kill -9` at
randomised offsets, N ≥ 200 iterations, biased toward the checkpoint boundary (the ±200 ms
window around each 5 s mark is where the interesting interleavings live).

Every survivor must satisfy, per channel:

1. `sum(*_frames over all segments) >= wav_header_frames` — the §7 direction.
2. excess `<= 80 000 frames` (one 5 s checkpoint).
3. `wav_header_frames <= (filesize − 44) / 2` — catches a **torn 4-byte length field**,
   which is the one way "the fields only ever grow" can be defeated. §7 assumes that write
   is atomic; on APFS it effectively is, but it is not guaranteed, so it gets asserted
   rather than assumed.
4. `ffprobe` decodes the file and reports a duration within 5 s of the declared length —
   this is `SPEC.md:389`'s "playable, valid WAV header".
5. tail loss `<= 5 s` (§13).
6. `segments.json` parses — it is written temp+rename, so a partial file is a bug.

**Assertion 4 runs on the unrepaired file.** `meet-rec repair` is tested separately
(§6 below) and must never be in the path that makes this gate pass.

Known non-assertion: after `kill -9`, segments-derived duration will **not** equal
`ffprobe` duration. That is assertion 1 working, not a failure. Recording it here because
it is the obvious wrong test for someone to write later.

---

#### 6. `meet-rec repair` — accepted, tested apart from the gate

Rune offered it; I accepted with conditions. Its own tests, none of which touch the §5 gate:

- Repairs a stale-header file to `(filesize − 44) / 2` frames, drops a trailing partial frame.
- Recovered audio is byte-identical to what the unrepaired file was missing.
- **Refuses** a file whose header already matches the data — no silent no-op rewrite.
- **Never runs implicitly.** A test asserts `meet-rec` itself never invokes it.

#### 7. The live gate runs

The SPEC gate is one 45-minute call with an AirPods swap mid-way. Because a swap closes the
segment (`SPEC.md:89`) and re-anchors drift to the host clock, that single run yields two
~22-minute segments — and `FINDINGS.md:138` puts the failure at the 30-minute mark. **As
specified, the gate run can pass without ever reaching the window the risk lives in.**

So, two runs:

| Run | Duration | Certifies |
|---|---|---|
| **A — continuous** | 45 min, no device change | The drift number. One segment, ~540 anchors, 45 min of continuous measurement |
| **B — switch** | 45 min, AirPods connect + disconnect mid-call | Survival, segment continuity, §11 gap number, then `kill -9` at the end |

Run A produces the number that goes on the gate. Run B produces the swap and crash evidence.
Both are recorded by me with no other participants (see the clearance note below).

Evidence captured per run: full `drift-check` stdout, `ffprobe` on both files,
`segments.json`, anchor count vs expected (2700 / 5 = 540 ±1 per channel), and the
per-channel + cross-track numbers from F4.

#### The four gate lines, verbatim from `SPEC.md` §5

> **45-min real Zoom call: both files intact, drift < 200ms end-to-end, survives an
> AirPods switch mid-call, survives `kill -9`**

I am not inventing criteria around these. Each line below is one of those four,
plus the evidence that would let me sign it off.

##### G1 — both files intact and playable

- `ffprobe` both tracks: expect `pcm_s16le / 16000 Hz / 1 ch` on each, per the contract §2.
- Declared header frame count vs. actual data-chunk bytes on disk: report both numbers.
- Decode end to end with `hound`; any decode error fails the gate.
- Non-silence check per track (RMS over 1 s windows), so an "intact" file that is
  44 bytes of header and 45 minutes of zeros cannot pass. A clean, playable, empty
  recording is a failure, not a pass.

**Evidence:** `ffprobe` output for both files, byte/frame counts, per-track RMS summary.

##### G2 — drift < 200 ms end-to-end, with the measured number

**Blocked on a format change.** Raised on [TUR-4](TUR-4.md) as item 1.

With `segments.json` as currently specified, a no-device-switch 45-minute call is a
single segment carrying one `start_host_ns` and two frame counts. The only computable
quantity is `(mic_frames − sys_frames) / 16000`, which:

- has no host-clock reference, so common-mode drift (both clocks sliding the same way —
  likely when mic and output are the same device) cancels to ≈0 and reads as a pass;
- conflates genuine drift with the teardown skew the contract §6 already warns about;
- can be structurally constant if `rubato` runs at a fixed 3:1 ratio off input frames.

Asked for instead: **per-checkpoint anchors** `{host_ns, mic_frames, sys_frames}`, one
per 5 s flush (~540 over 45 min, tens of KB). Then per channel:

```
drift_ch(t) = frames_ch(t)/16000 − (host_ns(t) − start_host_ns)/1e9
```

**Evidence:** max |drift| per channel, final drift per channel, inter-channel drift,
the minute of first 200 ms crossing if any, and the full curve as a CSV attachment.
Minimum acceptable fallback if anchors are refused: per-channel
`mic_end_host_ns`/`sys_end_host_ns` from the IO callback's `mHostTime`. That yields one
endpoint number and no curve — enough to sign off, not enough to see the 30-minute
silent failure early.

##### G3 — survives an AirPods switch mid-call

- Expect ≥ 2 segments, with segment 1 carrying a device-change `reason`.
- Contract §5 says the boundary is a real, unpadded gap. Report the gap in ms:
  `start_host_ns[1] − last_anchor.host_ns[0]` (needs the same anchors as G2; without
  them the gap is not measurable and I can only assert "a boundary exists").
- Audio continuity across the boundary: known-signal fixture, assert the signal resumes
  and the only loss is the reported gap.
- Both tracks still decode; header/segment sum invariant (G4) still holds.

**Evidence:** segment table, measured gap in ms, continuity result.

##### G4 — survives `kill -9`

- Kill at randomised offsets, including deliberately mid-checkpoint, repeated.
- Assert the achievable invariant rather than the stated one:
  `sum(*_frames across segments) >= wav_header_frames`, equality on graceful stop.
  Strict equality across two non-atomically-written files cannot hold under an
  arbitrary kill; raised as item 2 on [TUR-4](TUR-4.md), together with the
  write ordering (`segments.json` rename first, WAV header second) that keeps the
  crash window in the benign direction.
- Tail loss ≤ checkpoint interval (5 s as specified), file playable, header valid.

**Evidence:** kill-offset table with per-run invariant result and measured tail loss.
