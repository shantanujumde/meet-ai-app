## Description

Spun out of TUR-127's investigation (mic-permission-denial recording bug).

While reproducing TUR-127 on real hardware, Tess found:
- Two duplicate "meet-ai" entries under System Settings → Privacy & Security → Microphone for what should be one app.
- `tccutil reset AudioCapture pro.saleschat.meetai` reported resetting **4** separate stale entries in one call.
- After that reset, the "System Audio Recording Only" list — which had zero entries for meet-ai right after the reset — showed **three new meet-ai entries afterward, defaulted to ON**, with no consent prompt ever shown.

Likely cause: re-signing across builds is producing distinct TCC client identities (FINDINGS.md §10.4 — TCC keys the grant to the designated requirement: bundle ID + certificate leaf for an identity-signed build, or the binary's cdhash for ad-hoc). If different local builds/signing passes end up under different designated requirements, each looks like a "different app" to `tccd`, so toggling one visible row in System Settings doesn't necessarily touch the identity the currently-running signed binary actually authenticates as — the running process can end up using a different, still-granted TCC record than the one the tester just switched off.

This doesn't change the code fix in TUR-127 (which checks `AVCaptureDevice.authorizationStatus(for: .audio)` from inside the running process, so it reads whichever identity that process actually has — correct regardless of how many stale rows exist). But it makes **manual gate testing** (TUR-95 step 7, TUR-115) unreliable and confusing: a tester can toggle the wrong row off and see permission still "granted" through no fault of the app.

#### Ask
Investigate why re-signing/rebuilding produces multiple TCC identities for the same bundle ID, and whether a consistent local signing identity (SETUP.md §10.3's `meet-ai Local Signing` cert) across dev rebuilds prevents it. Document a reliable `tccutil reset` + re-test recipe for the TUR-95 gate so future permission-revoked runs use the same identity every time.

Not blocking — cleanup/tooling hygiene, not a functional bug in the shipped app.

## Comments (1)

### Rune · 2026-09-28 15:00 UTC

> Investigated live on real hardware (not just reading old FINDINGS). Reproduced Tess's exact numbers:
>
> **`tccutil reset AudioCapture pro.saleschat.meetai` printed 4 identical success lines**, live, on this machine. Cause: `tccutil reset <service> <bundle-id>` resolves the bundle ID through LaunchServices to *every* registered app matching it, not to one TCC row. `mdfind "kMDItemCFBundleIdentifier == 'pro.saleschat.meetai'"` found 4: the real build, the phase0a spike build, and stray copies in ~/Downloads and ~/Applications. Three share the current signing identity's cert leaf (`eafb73d2…`); the phase0a spike build is still signed against the *first* identity this project ever minted (`be3fb2c8…`, §10.3's own example value) — same bundle-ID string, genuinely different designated requirement, because it was never rebuilt after the identity was rotated once, early in the project's history. That's the ticket's hypothesis, confirmed exactly, not just plausible.
>
> Second, independent cause: permanent path-keyed TCC rows from pre-TUR-10 ad-hoc builds (already documented in FINDINGS §10.6) are still live on this machine — 4 of them across Microphone/AudioCapture — and display as "meet-ai" too since the build directories they point at still exist. `tccutil reset` can't reach them; a tester comparing before/after can easily mistake their continued presence for a fresh unprompted grant.
>
> The signing identity itself is *not* actively drifting — `make-identity.sh`'s idempotency guard (TUR-10) works, confirmed only one identity in the keychain right now. The duplication comes from old build outputs and stray installed copies that were never rebuilt/cleaned after the one historical rotation, plus permanently-stuck ad-hoc-era rows.
>
> Wrote this up with full evidence and a copy-pasteable reset+retest recipe in **FINDINGS.md §11** (5 subsections: root causes A/B/C, a bonus justfile bug, and the recipe), with a pointer added from SETUP.md's Step 8 gate instructions.
>
> **Bonus fix**: found and fixed a real bug in `justfile`'s `sign` recipe while verifying the identity resolves consistently — it computed `SIGN_KEYCHAIN` off raw `$HOME` instead of the account's real home (dscl), unlike `make-identity.sh`/`build.sh` which were already hardened for exactly this in TUR-10. Under any redirected-`$HOME` session (confirmed live under this very Paperclip run: `$HOME` here is a per-run temp dir), `just sign` silently fell through to no `--keychain` and would fail to find the identity at all ("0 valid identities" against the default search list). Fixed to use the same dscl fallback; re-verified `just sign` now correctly signs against `pro.saleschat.meetai` + the current cert leaf even with `$HOME` redirected.
>
> Committed as d8d58ce on `docs/releasing-guide` (FINDINGS.md, SETUP.md, justfile).
>
> Note: this investigation ran real `tccutil reset` commands against the dev machine's actual TCC database (Microphone + AudioCapture for `pro.saleschat.meetai`) as part of reproducing the bug — that grant will need to be re-approved next time the real app requests it, same as any other gate reset.
>
> Not done: the one-time manual cleanup of the 4 permanently-stuck path-keyed rows (needs System Settings GUI or TCC.db surgery, out of scope for an unattended change to someone's permission database) and rebuilding/removing the 3 stale registered copies found by mdfind. Both are called out explicitly in FINDINGS §11.5 step 1 and step 6 as the first thing whoever runs the next TUR-95/115 gate should do.
