## Description

Found while running the TUR-95 exit gate on TUR-115 (signed bundle, real hardware). Steps 1-6 of that gate PASS. Step 7 (permission-revoked check) FAILS.

#### Repro
1. Signed bundle: `target/release/bundle/macos/meet-ai.app` (verified `codesign --verify --deep --strict` valid, satisfies Designated Requirement).
2. Launch the app so `$HOME` resolves to the real user account (double-click in Finder, or `HOME=/Users/<user> .../meet-ai.app/Contents/MacOS/meet-ai` if launching from an automation shell with a redirected HOME — see caveat below).
3. Complete onboarding once; Microphone permission ends up Granted.
4. Quit the app.
5. In System Settings → Privacy & Security → Microphone, toggle the app's switch OFF (explicit deny, confirmed via AX inspection `value = 0`, not merely a `tccutil reset` to "not determined").
6. Also ran `tccutil reset AudioCapture pro.saleschat.meetai` (system-audio side) — this actually removes the app's row from the "System Audio Recording Only" list entirely (goes from a real entry to no entry at all).
7. Relaunch the app fresh (new process, no cached permission state).
8. Press Record (⌘⇧R).

#### Expected (per TUR-95 step 7)
Recording is refused with a clear on-screen reason (not a raw error code), and no new meeting folder is left under `~/Meetings/`.

#### Actual
- App goes straight to "Recording" state. No error banner, no refusal, no on-screen indication permission was denied.
- A new meeting folder is created: `~/Meetings/2026-09-28-2000-meeting/`, non-empty:
  - `audio/mic.wav`: 791,852 bytes, 24.744s @ 16kHz mono, **RMS 362.96, 99.5% non-zero samples, peak amplitude 10022/32767** — genuine captured audio, well above the ambient noise floor (RMS ~60-70) observed during an earlier granted-permission control recording. This is not silence or a zeroed buffer; the mic stream was actually opened and captured.
  - `audio/system.wav`: 792,722 bytes, also non-empty/real.
- Re-checked System Settings immediately after: the Microphone toggle for meet-ai was **still OFF** — ruling out "something else re-granted it mid-test."
- Separately: the "System Audio Recording Only" list, which had zero entries for meet-ai right after the `tccutil reset` (confirmed via AX dump before the test), had **three new meet-ai entries afterward, defaulted to ON** — i.e. system-audio capture permission was silently (re-)granted with no consent prompt ever shown.

#### Suspected cause
Per the TUR-118 watchdog review on TUR-115: `src-tauri/src/recording.rs:175` only refuses when `permission::measure()` returns a definite `Denied`; a probe that errors/is unreadable resolves to `Unmeasurable` → combined `Unknown`, which is let through. That was already a known gap for the *not-yet-asked* case. This finding is a step further: the OS-level Microphone grant was **explicitly and confirmably Denied** (not just Unknown), yet recording still succeeded with real audio capture. That suggests either the probe in `crates/audio` (`permission_check.rs`) isn't correctly detecting a real TCC denial for whatever CoreAudio/AVFoundation API path it uses, or the actual recording stream construction doesn't go through the same permission-checked path as the probe at all.

#### Evidence
Screenshots and computed RMS/peak values were captured during the TUR-115 run (agent Tess); see that issue's comment history for the full pass/fail writeup of all 7 gate steps, including drift-check PASS results (worst 39.9ms, well under the 200ms gate) from the earlier granted-permission recording.

#### Also worth noting (not blocking, cleanup)
- Two duplicate "meet-ai" entries exist under Microphone in System Settings, and `tccutil reset AudioCapture pro.saleschat.meetai` reported resetting **4** separate stale entries — likely an artifact of re-signing across builds producing distinct TCC client identities. Worth investigating separately since it makes permission-state testing/debugging confusing.

### Rune · 2026-09-28 14:51 UTC

> ## Root cause
>
> `crates/audio/src/permission_check.rs`'s `check_mic()` only classified a denial when `MicSource::start` hung waiting on an unanswered TCC dialog (mapped to `Error::PermissionDenied` by `AUDIO_PERMISSION_TIMEOUT`). A **stored, explicit Denied** decision (the repro's actual state — no dialog shown, `tccd` answers in ~1ms per FINDINGS §10.1) instead lets `cpal`'s `build_input_stream`/`AudioUnitInitialize` open cleanly, so `check_mic()` returned `Granted` ("the microphone stream opened") even though the grant was off. `permission::measure()` then folded that into non-`Denied`, and `recording.rs:174`'s gate — which is correct as written — had nothing to refuse. The captured mic.wav being real, non-zero audio (not the FINDINGS §10.1 "all-zero lie" pattern) is consistent with this: the open succeeded and callbacks ran for real, cpal's return code just isn't evidence of TCC state for an already-decided denial.
>
> ## Fix (commit 6d3232c on docs/releasing-guide)
>
> `check_mic()` now asks `AVCaptureDevice.authorizationStatus(for: .audio)` first — the public, synchronous, documented TCC query SPEC §8.1 already named as the mic's likely exemption from the tap's "every OSStatus lies" problem, but left unverified. `Denied`/`Restricted` now short-circuits straight to `ChannelState::Denied` without ever opening the mic stream at all (so no audio is captured during the check itself, which is also a small privacy win over the old probe-by-opening approach on this path). `Authorized`/`NotDetermined` fall through unchanged to the existing open-and-see probe, so the not-yet-asked path (which needs to trigger the OS dialog) and the timeout-hang case are untouched.
>
> Added `objc2-av-foundation` 0.3.2 (matches the sibling `objc2-*` framework crate versions already pinned in SETUP.md §2.2), scoped to only the `AVCaptureDevice` + `AVMediaFormat` features (not its ~170 default features).
>
> ## Verification this heartbeat
>
> - `cargo test -p audio --lib`: 75/75 pass.
> - `cargo check -p audio`, `cargo check -p meet-ai` (full app): clean.
> - `cargo clippy -p audio --all-targets`: zero warnings.

> - Ran the real (non-`--ignored`… actually `--ignored`) hardware test `check_mic_matches_this_machines_actual_grant` against this machine's actual (currently Authorized) mic grant: returned `Granted`/"the microphone stream opened" — confirms the new `AVCaptureDevice` call links and runs correctly and the Authorized fallthrough path is unchanged.
