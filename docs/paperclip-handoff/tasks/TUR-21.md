## Description

Follow-up from TUR-18, approved by the board.

#### The problem

All seven agents share one Claude connection. When that connection refuses a session — usage limit reached, or access refused — every agent that tries to start a run dies in 1-4 seconds having done nothing: zero tokens, no tool calls, no partial turn. The run is recorded as failed and the agent then sits still.

Nothing wakes it back up. On 2026-09-27 that meant Rune sat dead for about four and a half hours on TUR-10 while Vox and Tess committed contract changes on top of its work. Recovery took a manual sweep: someone had to notice, read the run logs, and hand-ping each agent on its own issue.

This will happen again the next time the limit is hit.

#### What to build

An automatic re-ping, so a connection-level stop heals itself instead of waiting for a person.

The mechanism already exists in the platform: `PUT /api/issues/{id}/watchdog`, which accepts `{ "agentId": "...", "instructions": "..." }` and is open to agents, not just the board. A watchdog agent is attached to an issue and is triggered when the issue goes quiet. I confirmed the endpoint shape and that an agent can create and delete one.

Steps:

1. Confirm what actually fires a watchdog — the trigger condition, how often it checks, and whether a failed run counts as "quiet". Check `monitorNextCheckAt` / `monitorAttemptCount` on the issue record and `GET /api/issues/{id}/diagnostics/wakes`.
2. Write the watchdog instructions: read the last run log, decide whether the failure was a connection-level stop (session opens, `usage updated: 0/200000`, then a single `acpx.error` within seconds) or a real failure in the agent's own work. Only re-ping for the first kind. A real failure should stay failed and get escalated, not retried in a loop.
3. Back off rather than hammer. A usage-limit stop clears on its own after a while; retrying every minute burns the limit further and helps nobody. Space the attempts out and give up after a few, leaving a comment that names what it tried.
4. Attach a watchdog to each live agent issue: TUR-10 (Rune), TUR-17 (Nia), TUR-15 and TUR-13 (Vox), TUR-14 and TUR-7 (Tess), TUR-12 (Leo).
5. Decide who watches the watchdog. If Alen is the watchdog agent and Alen is also stopped by the same shared connection, nothing fires. Either pick an agent that runs on a different connection, or add a board-level timer as the outer backstop.

#### Done when

An agent stopped by a connection-level failure is running again without a person intervening, and the recovery attempt is visible in the issue thread. Verify by checking that a watchdog fires at all before wiring up all seven.

#### Known limits

- Agents cannot call `clear-error`; the stale red flag on the board still needs a board-level clear. Worth raising separately as a platform ask.
- This treats the symptom. The underlying cause is one shared connection for seven agents. Separate connections, or a queue in front of the shared one, would remove the failure mode rather than patch it.

## Document: Connection-stop auto-recovery — design and findings

_Key `connection-stop-auto-recovery`, last updated 2026-09-27 13:36 UTC._

### Connection-stop auto-recovery (TUR-21)

When the shared Claude connection refuses a session, every agent that tries to
start a run dies in a few seconds having done nothing. Nothing used to wake them
back up. This is what does.

#### What was actually wrong

The platform already retries these failures — but only three times, about sixty
seconds apart (`scheduledRetryReason=transient_failure`, attempts 0, 1, 2). A
usage limit lasts hours, so on 2026-09-27 all three retries were spent inside
three minutes and every agent then sat still. Rune was dead from 08:40 to 13:15,
about four and a half hours, until a person hand-pinged it.

So the gap was never "no retry". It was "no retry on a horizon longer than three
minutes". Everything here is the long-horizon layer that runs after the
platform's own ladder gives up.

#### The signature

A connection-level stop looks like this in the run log:

```
acpx.status  session/new ... model claude-opus-5
acpx.status  usage updated: 0/200000
acpx.status  session updated
acpx.error   stopReason: ACP agent reported a terminal limit failure.
```

Open, no usage, error, exit — inside about four seconds. On the run record:

| field | value |
|---|---|
| `status` | `failed` |
| `errorCode` | `acpx_turn_failed` |
| `error` | `...terminal limit failure.` or `...terminal access failure.` |
| duration | under 2 minutes (observed: 4–6s) |
| `usageJson.costUsd` | exactly `0` |

Checked against all 86 runs in the incident window, those five conditions select
31 runs, every one of them a genuine door-refusal, and exclude all 14 runs that
did real work. **Do not use `inputTokens`/`outputTokens` to detect "no work
done" — the platform leaves them `null` on every failed run.** `costUsd` is the
field that actually distinguishes.

##### Runs that hit the limit mid-work are deliberately not retried

The first failures of the incident were long and expensive — up to 1548s and
$7.58 — because agents were part-way through a turn when the limit landed. Those
are left alone on purpose. Re-pinging an agent that just burned the limit pushes
the connection further under, and it is unnecessary: the next attempt on a
limited connection is always refused at the door, producing the zero-cost
signature above. The narrow rule still catches the tail of every incident, which
is the part where the agent is sitting still.

#### The two layers

**Outer backstop — a cron routine.** "Connection-stop auto-recovery sweep"
(routine `84ff28d8`), assigned to Alen, fires every 30 minutes, creates a child
issue under TUR-21, runs `connection_stop_sweep.py`, and closes itself. Quiet
sweeps post nothing.

**Inner, faster path — per-issue watchdogs.** Attached to TUR-7, TUR-10, TUR-12,
TUR-13, TUR-14, TUR-15, TUR-17 and TUR-21, with Alen as the watchdog agent. The
platform fires these when an issue goes quiet, comparing a fingerprint of issue
state against `lastReviewedFingerprint`. They run the same script.

Both layers share one state file, so they cannot double-ping: the backoff ladder
is keyed by failed run id, not by who noticed.

##### Who watches the watchdog

No agent escapes this failure. All seven are `claude_local` with no per-agent
connection override, so picking a "different" agent as watchdog would be a false
sense of independence — there is no second connection to move anyone to, and
creating one needs board access.

Independence comes from the **scheduler**, not the agent. The cron trigger lives
platform-side and needs no Claude session to fire. If a tick's run dies on the
refused connection, the tick thirty minutes later tries again, and keeps trying
until the connection comes back. The watchdogs self-heal the same way: a run
that dies without writing anything leaves `lastReviewedFingerprint` unchanged,
so the next sweep re-fires it.

That is also why the backoff matters. `POST /api/heartbeat-runs/{runId}/watchdog-decisions`
with `{"decision":"snooze","snoozedUntil":...}` is how a watchdog run tells the
platform to stop re-firing; without it, self-healing becomes hammering.

#### Backoff

Re-pings are due 15, 45 and 120 minutes after the failure, then the sweep posts
one comment naming every attempt and stops touching that incident. State is
keyed by failed run id, so a fresh failure starts a fresh ladder, and an issue
that recovers has its state dropped.

Against the real incident, Rune's first re-ping would have landed at 08:55
instead of 13:15 — four hours and twenty minutes earlier.

#### Running it by hand

```bash
python3 connection_stop_sweep.py --dry-run   # report only, change nothing
python3 connection_stop_sweep.py             # re-ping where due
```

Needs `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY`, `PAPERCLIP_COMPANY_ID`.

#### Known limits

- **This treats the symptom.** The cause is seven agents on one connection.
  Separate connections, or a queue in front of the shared one, would remove the
  failure mode instead of patching it.
- **The stale red flag stays.** Agents cannot call `clear-error`, so a recovered
  agent still shows an error on the board until someone clears it. Worth raising
  as a platform ask.
- **The platform's own 3×60s ladder is still wrong** for this failure and still
  burns three attempts instantly. Widening it platform-side would make most of
  this unnecessary.
- **Not yet observed recovering a live stall.** The detection and decision logic
  is verified against the real incident data, and the delivery path is verified
  live (routine → issue → run → sweep). But no agent has been stopped since this
  went in, so the first real proof is the next incident.

> **Auto-recovery is live.** Two layers, both verified.
>
> ### What I found first
>
> The platform already retries these failures — three times, sixty seconds apart
> (`scheduledRetryReason=transient_failure`, attempts 0/1/2). That is why nothing
> looked broken. A usage limit lasts hours, so on 2026-09-27 all three retries
> were spent inside three minutes and every agent then sat still. The gap was
> never "no retry", it was "no retry on a horizon longer than three minutes".
>
> ### The detector
>
> A connection stop is identifiable from the run record alone — no log parsing:
> `status=failed`, `errorCode=acpx_turn_failed`, error text naming a terminal
> limit or access failure, under two minutes, and `costUsd` exactly 0.
>
> Across all 86 runs in the incident window those five conditions select 31 runs,
> every one a genuine door-refusal, and exclude all 14 runs that did real work.
> One trap worth recording: **`inputTokens`/`outputTokens` are `null` on every
> failed run**, so they cannot be used to detect "no work done". `costUsd` can.
>
> Runs that hit the limit *mid-work* (up to 1548s and $7.58) are deliberately not
> re-pinged — that would push the connection further under, and it is unnecessary,
> because the next attempt is always refused at the door and produces the
> zero-cost signature we do act on.
>
> ### The two layers
>
> - **Outer backstop:** routine "Connection-stop auto-recovery sweep", every 30
>   minutes, runs the sweep script and closes itself. Quiet sweeps post nothing.
> - **Inner path:** per-issue watchdogs on TUR-7, TUR-12, TUR-13, TUR-14, TUR-15,
>   TUR-17 and TUR-21.
>
> Backoff is 15, 45 then 120 minutes from the failure, then it escalates with a
> comment naming every attempt. State is keyed by failed run id, so both layers
> share one ladder and cannot double-ping.
>
> ### Who watches the watchdog
>
> Nobody can, by picking a different agent — all seven are `claude_local` on the
> one connection with no per-agent override, and creating a second connection
> needs board access. Independence comes from the **scheduler** instead: the cron
> trigger is platform-side and needs no Claude session to fire, so if one tick's
> run dies on the refused connection, the next tick thirty minutes later tries
> again until it gets through.
>
> ### Verified
>
> - Routine fired end to end: cron → TUR-25 → run → sweep → issue closed.
>   Output: `sweeping 18 live agent-assigned issues / done; 0 issue(s) needed action`.
> - Watchdogs fire: TUR-13 and TUR-7 triggered at 13:34:50, spawning TUR-26 and
>   TUR-27.
> - Replayed against Rune's real timeline: first re-ping would have landed at
>   **08:55 instead of 13:15** — four hours twenty minutes earlier.
>
> ### Not yet proven
